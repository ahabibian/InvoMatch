Base44 Phase B Prompting Boundary
Mini-EPIC 33.4 — Pilot UI Phase B Core Review Path Construction Authorization & Base44 Review-Surface Execution Boundary

Purpose

This document defines the prompting boundary that governs the first Base44 construction instruction for Phase B of EPIC 33.

Mini-EPIC 33.4 is the first point at which Base44 may be directly instructed to construct workflow-adjacent review surfaces inside the accepted Pilot UI shell established by Mini-EPIC 33.3.

Because generative UI tools can overbuild, populate empty surfaces with fake operational data, invent dashboard metrics, fabricate evidence semantics, or prematurely introduce correction and outcome behavior, the Phase B prompt must remain tightly controlled.

The prompt is not a product imagination exercise.

It is an execution control surface for constructing only the authorized Phase B review path.

Prompting Principle

The governing prompt principle is:

Ask Base44 to construct only the approved Phase B core review path surfaces inside the accepted Phase A shell, and explicitly forbid it from generating fake business truth, fake review records, correction actions, finalization semantics, export readiness, or backend-like interpretation logic.

This prompting discipline protects the project from:

dashboard metric invention;
fake reconciliation queue population;
pseudo-operational review tables;
evidence interpretation fabricated for visual richness;
premature correction UI;
accidental simulation of finalized truth or export readiness;
phase drift from Phase B into Phase C, Phase D, or Phase E.
What the Phase B Prompt Must Request

The Phase B prompt must ask Base44 to build only the following surfaces.

3.1 Tenant / User Context Surface

Request:

activate the tenant/user context region already reserved in the Phase A shell;
keep it presentation-only;
show a structurally clear location for future workspace/user context;
avoid fake identity, fake permissions, or fake tenant status.

3.2 Pilot Dashboard Entry Surface

Request:

create a Pilot Dashboard as the structural entry point into the review path;
make it clear, professional, and B2B operational in posture;
include orientation content that explains the review path without claiming live metrics;
include a deliberate route or entry control toward the Review Queue.

The prompt must make clear that the Dashboard is:

not a KPI center;
not a reconciliation summary engine;
not a business-metric surface;
not a place to invent status counts.

3.3 Reconciliation Review Queue Surface

Request:

create a structural Review Queue surface;
define table/list/card posture suitable for future backend-bound review items;
include visibly provisional empty-state or placeholder structure;
explain that live review records are not yet bound in this phase;
maintain a clean route toward Match Detail / Evidence View.

The prompt may request column posture or list architecture.

The prompt must not request populated financial rows, sample invoices, fake vendors, fake amounts, fake mismatch examples, or any data that looks like product truth.

3.4 Match Detail / Evidence View Surface

Request:

create a structural detail/evidence screen;
build a clear inspection layout with future-facing evidence zones;
include the following zones or equivalent regions:
Source Record Zone;
System Interpretation Zone;
Evidence Comparison Zone;
Review Context Zone;
make each zone visibly structural and non-operational;
avoid any real or fake evidence conclusion.

The prompt must emphasize that this screen is:

an inspection-layout artifact;
not a backend interpretation engine;
not a decision screen;
not a correction screen;
not a finalization screen.

3.5 Navigation Path

Request:

preserve the accepted Phase A shell;
preserve persistent navigation;
create or refine a recognizable path:
Dashboard → Review Queue → Match Detail / Evidence View;
keep that path within Phase B scope only.

The prompt must not ask for navigation into:

Human Correction;
Finalized Truth Record;
Export Readiness Surface;
Intake Workspace;
trust/error/permission completion surfaces.
What the Phase B Prompt Must Explicitly Forbid

The Phase B prompt must explicitly prohibit Base44 from generating:

fake dashboard KPIs;
fake dashboard counts;
fake reconciliation metrics;
fake progress cards;
fake review summaries;
fake queue rows;
fake invoice records;
fake vendor names;
fake financial amounts;
fake mismatch examples;
fake review statuses;
fake confidence scores;
fake evidence verdicts;
fake interpretation text that sounds backend-derived;
fake acceptance/rejection conclusions;
approve buttons;
reject buttons;
correction buttons;
rematch buttons;
manual edit forms;
finalized truth records;
export readiness widgets;
intake/upload controls;
trust/error/permission system completion;
backend API calls;
live data integration;
frontend-generated reconciliation logic;
frontend-owned product truth.

These prohibitions must be present in the prompt itself, not merely assumed from surrounding governance documents.

Prompt Structure Requirements

The Base44 Phase B prompt should be structured in six parts.

Part 1 — Product Context

Explain briefly:

this is InvoMatch;
the interface remains a Pilot UI Layer only;
the backend remains the sole source of product truth;
Mini-EPIC 33.3 already created the shell/navigation foundation;
this prompt is only for Phase B Core Review Path Construction.

Part 2 — Shell Preservation Requirement

Specify that Base44 must:

preserve the accepted shell;
preserve persistent navigation;
reuse the shared layout frame;
build Phase B surfaces inside that frame;
avoid redesigning or replacing the shell.

Part 3 — Exact Build Request

Specify exactly what to create:

Tenant / User Context Surface;
Pilot Dashboard Entry Surface;
Reconciliation Review Queue Surface;
Match Detail / Evidence View Surface;
Dashboard → Queue → Detail/Evidence path.

Part 4 — Strict Non-Build Constraints

State concretely what must not be created.

This part must be exhaustive enough that Base44 is not invited to “helpfully” complete the workflow beyond Phase B.

Part 5 — Structural Quality Expectations

State that the output should be:

coherent;
professional;
enterprise/B2B operational in posture;
shell-aligned;
structurally clear;
expandable;
visibly non-operational where backend truth is not yet bound;
free of fake data and fake semantics.

Part 6 — Completion Check

Ask Base44 to return an implementation that:

reads as a controlled review-path surface layer;
does not read as a completed review workflow;
does not read as a live reconciliation system;
is ready for formal Phase B post-construction review.
Dashboard Prompt Discipline

The Dashboard portion of the prompt must be especially constrained.

The prompt may ask for:

orientation copy;
a restrained screen title;
a structural review-path card;
a navigational entry toward the queue;
non-metric explanatory layout.

The prompt may not ask for:

“useful stats”;
“dashboard insights”;
“status cards”;
“pipeline summaries”;
“recent reconciliation activity”;
“open issues count”;
“export-ready count”;
“matched/unmatched trends.”

Those phrases would invite Base44 to invent business truth.

Review Queue Prompt Discipline

The Review Queue portion of the prompt may ask for:

structural queue layout;
future-ready table or list posture;
empty state explaining that no backend-bound review records are active in this phase;
visually clear path toward evidence inspection.

The prompt may not ask for:

sample queue data;
realistic row examples;
fake records “for demonstration”;
illustrative invoice data;
example amounts;
placeholder statuses that look operational.

Those instructions would convert a structural queue into a fake ledger.

Evidence View Prompt Discipline

The Evidence View portion of the prompt may ask for:

structural evidence zones;
neutral explanatory labels;
clear reading hierarchy;
source/comparison/context regioning.

The prompt may not ask for:

generated evidence;
mismatch explanation;
confidence reasoning;
extracted value previews represented as operational;
recommendation text;
“system believes” language;
pass/fail claims;
“likely matched” or “requires correction” outputs.

Those instructions would turn a structural detail page into fabricated analysis.

Placeholder Discipline in Prompting

Any placeholder requested in the Phase B prompt must be:

explicit;
visibly provisional;
honest;
non-functional;
structurally meaningful;
clearly not backed by live product data.

The prompt must not use vague phrasing such as:

“fill gaps with realistic sample content”;
“make the tables look populated”;
“show what a real case would look like”;
“add representative metrics”;
“make the evidence card convincing.”

Those instructions would invite frontend-manufactured financial truth.

Prompting Failure Modes to Avoid

The following prompt failures are prohibited.

Failure Mode 1 — Over-Broad Review Product Prompt

Example problem:

Build the review workflow for InvoMatch.

This is invalid because it authorizes uncontrolled scope across Phase B and later phases.

Failure Mode 2 — Fake Dashboard Completeness

Example problem:

Create a dashboard with useful KPIs and reconciliation status.

This is invalid because Phase B Dashboard must not manufacture metrics.

Failure Mode 3 — Fake Queue Realism

Example problem:

Populate the queue with realistic invoice review records.

This is invalid because Phase B may define queue structure but not fabricate operational truth.

Failure Mode 4 — Evidence Semantics Leakage

Example problem:

Show evidence reasoning and why the match is suspicious.

This is invalid because Phase B Evidence View may construct zones, not backend-derived interpretation.

Failure Mode 5 — Correction Leakage

Example problem:

Add controls so operators can approve or correct an item.

This is invalid because Human Correction belongs to Phase C.

Failure Mode 6 — Finalization / Export Leakage

Example problem:

Show which records are finalized and ready to export.

This is invalid because finalized truth and export readiness belong to later phases.

Review Requirement After Prompt Execution

The Base44 result produced from the Phase B prompt must be reviewed against:

PHASE_B_CONSTRUCTION_AUTHORIZATION.md;
PHASE_B_EXECUTION_BOUNDARY.md;
PHASE_B_TARGET_CORE_REVIEW_PATH_ARTIFACT_DEFINITION.md;
PHASE_B_CONSTRUCTION_ACCEPTANCE_CRITERIA.md.

The prompt itself is not proof of compliance.

The generated artifact must be inspected for scope leakage, fake product truth, fake operational metrics, and premature entry into later phases.

Final Prompting Boundary Statement

Base44 may be instructed to construct the Phase B core review path surfaces inside the accepted Pilot UI shell.

It may not be invited to invent review truth, correction behavior, finalized outcomes, export semantics, backend interpretation, or fake financial product data for visual completeness.
