Mini-EPIC 33.13.P-NB — Backend Review Queue Row Collection API Gap / Implementation Requirement

Purpose

This document defines the backend Review Queue row collection API gap and implementation requirement.

The refined discovery confirmed that backend review primitives exist.

The refined discovery did not confirm a Base44-facing Review Queue row collection contract.

Therefore, the project must define the required backend contract before Base44 can bind Review Queue to real backend-owned rows.

This document does not implement the endpoint.

This document does not bind Base44.

This document does not create fake rows.

This document does not validate live Match Detail payload rendering.

This document does not claim Scenario 15 completion.

Source Discovery

The source discovery record is:

docs/architecture/BACKEND_REVIEW_QUEUE_ROW_CONTRACT_DISCOVERY_RECORD.md
Gap Decision

A backend Review Queue row collection API gap exists.

The gap is not absence of all review backend machinery.

The gap is absence of a confirmed Base44-facing row collection contract that Review Queue can call to obtain real backend-owned rows.

Backend review primitives exist, including review service behavior, review integration behavior, run review API behavior, and review persistence.

However, these primitives are not yet confirmed as a Base44-facing Review Queue row collection endpoint.

Required Backend Endpoint Shape

The project must provide or confirm a backend endpoint that returns Review Queue rows.

The preferred endpoint shape is:

GET /api/review/queue

An alternative run-scoped endpoint may be accepted only if the product explicitly decides Review Queue is run-scoped:

GET /api/reconciliation/runs/{run_id}/review

If the run-scoped shape is used, Base44 must have a clear backend-owned run_id source.

No frontend-created run_id may be used as live validation evidence.

Required Row Contract

Each Review Queue row returned by the backend must include one backend-owned identifier.

Acceptable identifier fields include:

case_id
review_id
review_item_id
match_id
matchId
reviewId
match_id
review_id

The selected identifier must map to the Match Detail lookup contract.

The row contract must distinguish the row identifier from display-only labels.

The row contract must not require Base44 to compute financial meaning.

Minimum Row Fields

The backend row contract should provide only bounded display-only fields needed for operator recognition.

Allowed row fields include:

id or case_id
run_id, if required for lookup or operator context
match_id, if backend-owned and needed for Match Detail lookup
status
reason_code or review_reason
invoice_summary_label
payment_summary_label
amount_summary, if backend-computed
date_summary, if backend-computed
created_at or updated_at
trace_id or audit_reference

All fields must be display-only in Base44.

Forbidden Row Fields Or Behavior

The Review Queue row collection contract must not require or encourage Base44 to receive or create:

raw evidence lists for Match Detail
confidence calculations performed in Base44
frontend-generated export readiness
frontend-generated permission conclusions
finalized truth generated by frontend
reviewed_payload
internal-only reviewer fields
backend-private audit internals
fallback sample truth
fake row payloads used as live validation evidence
Required Failure Behavior

The endpoint or contract must define failure behavior for:

no active review rows
unauthorized access
forbidden tenant access
missing run context where applicable
unavailable review store
invalid or incomplete row shape
unknown identifier passed later to Match Detail

Base44 must render these as visible failure or empty states.

Base44 must not replace failures with fake rows.

Tenant And Security Requirements

The row collection endpoint must respect tenant isolation.

The row collection endpoint must respect authenticated user context if authentication is enabled.

The row collection endpoint must not leak rows across tenants.

The row collection endpoint must not expose internal reviewer payloads to unauthorized users.

The endpoint must align with existing security and authorization services where applicable.

Match Detail Handoff Requirement

Review Queue must pass only the selected backend-owned identifier to Match Detail.

Review Queue must not pass evidence.

Review Queue must not pass confidence.

Review Queue must not pass export readiness.

Review Queue must not pass permission conclusions.

Review Queue must not pass finalized truth.

Review Queue must not assemble Match Detail payload data.

Match Detail remains responsible for fetching backend-governed detail data using the identifier.

Implementation Requirement

A future implementation mini-epic must do one of the following:

Option A: Confirm and document an existing Base44-facing Review Queue collection endpoint.

Option B: Implement a new backend Review Queue collection endpoint.

Option C: Explicitly decide that Review Queue is run-scoped and define how Base44 obtains a backend-owned run_id without frontend invention.

If none of these is possible, live Match Detail validation remains blocked.

Required Tests For Future Implementation

Future backend implementation must include tests for:

successful row collection response
empty queue response
unauthorized response
forbidden or tenant-isolated response where applicable
row shape excludes internal fields
row shape includes backend-owned identifier
row identifier can be used for Match Detail handoff
response does not expose reviewed_payload
response does not expose reviewed_by
response does not require frontend truth synthesis
Acceptance Conditions For Future Binding

Base44 Review Queue binding may be considered only after:

a backend row collection endpoint is confirmed or implemented
the endpoint returns backend-owned rows

tests validate the row contract

Match Detail can handle the identifier without frontend truth synthesis
Forbidden Workarounds

The project must not:

create fake rows to satisfy live validation
treat demo handoff as backend row validation
treat internal service primitives as product API availability without endpoint confirmation
bind Base44 to unverified internal assumptions
assemble Review Queue rows in frontend logic
pass Match Detail payload through Review Queue
claim Scenario 15 completion before backend-owned row behavior is validated
